# Bitrix24: программный режим «только чтение» для элементов CRM

Модуль `mtai.readonly` позволяет **программно** переводить элементы CRM —
сделки, контакты, компании и смарт-процессы — в режим «только чтение»
поверх штатных прав, по любому условию: значение поля (например,
`UF_BLOCKED = Y`), параметр сессии, группа пользователя, внешний сервис —
что угодно.

Главный принцип: **права можно только сузить**. Если у пользователя
штатными ролями разрешено редактирование — модуль может запретить его
для конкретного элемента по условию. Если штатно разрешено только чтение —
модуль **не может** (и не пытается) выдать право на редактирование.

Второй принцип: **по умолчанию блокируется только веб-интерфейс**.
Программный доступ — CLI-скрипты, агенты, роботы, REST и вебхуки —
свободно обновляет сущности (опция «Блокировать также программные
изменения» возвращает строгий режим «везде»).

```php
// программный обход на любом участке кода:
Manager::getInstance()->withBypass(fn() => $deal->Update(11, $fields));
```

## Для какой редакции предназначен

Только для «Битрикс24» (тестировалось на Bitrix 26.750.0, модуль `crm`).
Используются Factory API CRM (`Bitrix\Crm\Service\...`), классические
события `OnBeforeCrm*Update/Delete` и ORM-события таблиц смарт-процессов.

## Как это работает

Механизм состоит из четырёх слоёв:

0. **Интеграция с системой прав CRM** (`Bootstrapper` + декоратор
   `UserPermissions`, регистрируется на `OnProlog` — после авторизации, но до
   запуска компонентов). Для текущего пользователя в ServiceLocator
   подменяется объект проверки прав: методы `canUpdateItem`/`canDeleteItem`/
   `canChangeStage`/… дополнительно возвращают `false` для заблокированных
   элементов — только в канале UI (`Channel`: страницы и AJAX CRM);
   CLI/REST-запросы декоратор пропускает. Благодаря этому карточки **всех** типов — включая
   смарт-процессы, у которых нет параметра `FORCE_READONLY` — открываются
   в режиме просмотра ещё на сервере: редактор создаётся с `readOnly: true`,
   кнопки редактирования и inline-правка полей не отрисовываются, а операции
   сохранения отклоняются на `checkAccess`.

1. **Сервис правил** (`MTai\ReadOnly\Manager`) — вычисляет, находится ли
   элемент в режиме чтения для конкретного пользователя. Три источника
   (объединяются по ИЛИ):
   - **персистентные блокировки** `lock()` / `unlock()` — хранятся в БД
     (таблица `mtai_readonly_lock`), переживают перезагрузку;
   - **декларативные правила** из настроек модуля (JSON): `fieldEquals`
     (поле = значение) и `userGroup` (всем участникам группы);
   - **runtime-правила** `registerRule()` — любые PHP-callback'и
     (параметры сессии, дата/время, внешние условия).

2. **Жёсткий запрет на бэкенде** — даже если UI обойдён (REST, прямой
   вызов API, роботы), сохранение и удаление отклоняются:
   - сделки/контакты/компании — возврат `false` из событий
     `OnBeforeCrm{Deal,Contact,Company}{Update,Delete}` (вызываются как
     из современных Factory-операций, так и из legacy-API `CCrmDeal` и т.п.);
   - смарт-процессы — ORM-события `crm_items_<ID типа>OnBeforeUpdate/OnBeforeDelete`
     таблиц `b_crm_dynamic_items_<ID>` с отменой через `EventResult` с ошибкой.

3. **UI-резерв (`OnEndBufferContent`)** — страховка на случай, если слой
   прав не успел подключиться (например, что-то обратилось к правам CRM
   раньше `OnProlog`):
   - сделки/контакты/компании — инжектится одна перезагрузка со штатным
     параметром ядра `FORCE_READONLY=Y`;
   - смарт-процессы — редактор переводится в режим просмотра клиентски.
   Когда слой прав активен, инжект пропускается — карточка уже natively
   read-only без перезагрузок.

## Установка

1. Скопировать `local/modules/mtai.readonly/` в `local/modules/` портала.
2. Установить модуль в `Настройки → Модули` (или через API — см.
   `scripts/seed_readonly_demo.php` на тестовом стенде).

Модуль при установке:
- создаёт таблицу `mtai_readonly_lock`;
- регистрирует обработчики событий (классические, `OnEndBufferContent`
  и ORM-события всех существующих смарт-процессов).

## Публичный API

```php
use MTai\ReadOnly\Manager;
use MTai\ReadOnly\Rule\CallbackRule;
use MTai\ReadOnly\Rule\Context;
use MTai\ReadOnly\Rule\FieldEqualsRule;

$ro = Manager::getInstance();

// 1) Персистентная блокировка (в БД)
$ro->lock(\CCrmOwnerType::Deal, 11);              // для всех пользователей
$ro->lock(\CCrmOwnerType::Deal, 11, 4);           // только для пользователя 4
$ro->unlock(\CCrmOwnerType::Deal, 11, 4);         // снять персональную
$ro->unlockAll(\CCrmOwnerType::Deal, 11);         // снять все блокировки элемента

// 2) Проверка
$ro->isReadOnly(\CCrmOwnerType::Deal, 11);        // для текущего пользователя
$ro->isReadOnly(\CCrmOwnerType::Deal, 11, $userId);

// 3) Runtime-правило — любая логика (например, параметр сессии)
$ro->registerRule(
    new CallbackRule(
        fn(Context $c) => $c->entityTypeId === \CCrmOwnerType::Deal
            && ($c->getFieldValue('UF_BLOCKED') === 'Y')
    ),
    [\CCrmOwnerType::Deal], // ограничение по типам сущностей (опционально)
);

// Готовые правила:
new FieldEqualsRule('UF_BLOCKED', 'Y'); // поле элемента = значение
new \MTai\ReadOnly\Rule\UserGroupRule(9); // участникам группы — только чтение
```

Смарт-процессы идентифицируются своим `ENTITY_TYPE_ID` — тем же числом,
что в URL карточки: `/crm/type/1038/details/1/` → `1038`.

### Контекст правила

В callback приходит `MTai\ReadOnly\Rule\Context`:
- `$c->entityTypeId`, `$c->entityId`, `$c->userId`, `$c->isAdmin`;
- `$c->getItem()` — элемент через Factory API (лениво);
- `$c->getFieldValue('UF_...')` — значение штатного или UF-поля;
- `$c->getUserGroups()` — группы пользователя.

### Декларативные правила в настройках

Настройки модуля (`Настройки → Настройки модулей → CRM: режим только чтение`)
содержат чекбоксы «Модуль включён», «Применять к администраторам» и
**визуальный редактор правил** — таблица строк, без ручного JSON:

- **Условие** — «Поле = значение» (например UF-флаг блокировки;
  bool-подобные значения `Y` / `1` / `true` равнозначны) или
  «Группа пользователей» (выпадающий список групп портала);
- **Сущности** — множественный выбор: сделки, контакты, компании и все
  смарт-процессы портала (с их названиями); пусто = правило действует
  для всех типов;
- **Поле** — текстовый ввод с подсказками: при выборе сущностей в список
  подставляются их UF-поля;
- строки можно добавлять и удалять кнопками.

В опции `rules` хранится тот же JSON, что и раньше (формат не изменился,
его можно готовить и программно):

```json
[
    {"kind": "fieldEquals", "entityTypeIds": [2, 3, 4, 1038], "field": "UF_CRM_RO_DEMO", "value": "Y", "title": "Демо: флаг блокировки"},
    {"kind": "userGroup", "entityTypeIds": [2], "groupId": 9}
]
```

`entityTypeIds`: 2 — сделки, 3 — контакты, 4 — компании, ID смарт-процесса.
Без поля — правило применяется ко всем сущностям.

## Ограничения и особенности

- **Расширить права нельзя** — модуль только запрещает операции, которые
  штатные права разрешают.
- **Администраторы не блокируются по умолчанию** (опция «Применять к
  администраторам» выключена) — чтобы портал всегда можно было
  «разблокировать изнутри». Runtime-правила видят `$c->isAdmin` и могут
  решать сами, но общая опция имеет приоритет.
- ORM-гвард смарт-процессов ориентируется на **текущего пользователя
  запроса** (ORM-слой не знает контекста операции).
- При активном слое прав операции отклоняются на `checkAccess` с штатным
  сообщением «У вас нет прав…»; «красивое» сообщение «заблокирован…»
  дают гварды событий (пути без проверки прав, legacy-API).
- **Каналы**: CLI и `/rest/*` считаются программным доступом и по умолчанию
  не блокируются; робот/агент, запущенный внутри UI-хита, подпадает под
  блокировку — оборачивайте такие обновления в `withBypass()`.
  Мобильное приложение работает через REST и также считается кодом
  (включите `block_api`, если это не устраивает).
- Декоратор прав регистрируется только для запросов к `/crm/*`, `/rest/*`
  и AJAX-контроллерам — на остальных страницах работает экономнее.
- Кэш решений о режиме чтения живёт в рамках одного HTTP-запроса.
- При создании нового смарт-процесса обработчики для него регистрируются
  автоматически при первом открытии его карточки, при первом `lock()`
  его элемента или кнопкой в настройках модуля.
- UI-слой для смарт-процессов — best-effort: кнопки редактирования могут
  остаться видимыми, но сохранение гарантированно отклонится с понятным
  сообщением.

## Состав

- `local/modules/mtai.readonly/lib/Bootstrapper.php` — OnProlog-хук:
  регистрация декоратора прав в ServiceLocator.
- `local/modules/mtai.readonly/lib/Permissions/` — декораторы
  `UserPermissions` и `Item`-прав: сужение canUpdate/canDelete/canChangeStage.
- `local/modules/mtai.readonly/lib/Manager.php` — сервис: блокировки,
  правила, вычисление режима, регистрация ORM-обработчиков.
- `local/modules/mtai.readonly/lib/Rule/` — контекст и правила
  (`FieldEqualsRule`, `UserGroupRule`, `CallbackRule`, парсер JSON-настроек).
- `local/modules/mtai.readonly/lib/Guard/ClassicGuard.php` — запрет
  сохранения/удаления сделок, контактов, компаний.
- `local/modules/mtai.readonly/lib/Guard/DynamicGuard.php` — запрет
  сохранения/удаления элементов смарт-процессов (ORM-события).
- `local/modules/mtai.readonly/lib/Ui/Injector.php` — перевод карточки
  деталей в режим просмотра.
- `local/modules/mtai.readonly/lib/Internals/LockTable.php` — ORM-таблица
  персистентных блокировок.
- `local/modules/mtai.readonly/options.php` — страница настроек.
- `local/modules/mtai.readonly/install/` — установщик.

## Демо на тестовом стенде

На стенде `bitrix24_test` (см. корневой README стенда):

```bash
# установка модуля + UF-поле UF_CRM_RO_DEMO + демо-значения + правило
docker exec bitrix-php-1 php /var/www/html/local/tools/seed_readonly_demo.php

# прогон всех проверок (22 теста)
docker exec bitrix-php-1 php /var/www/html/local/tools/test_readonly_demo.php
```

Демо-элементы с `UF_CRM_RO_DEMO = Y`: сделка `/crm/deal/details/11/`,
контакт `/crm/contact/details/8/`, компания `/crm/company/details/1/`,
элемент смарт-процесса `/crm/type/1038/details/1/`. Под `test.user`
карточки открываются в режиме чтения и сохранение отклоняется; под
`admin` — штатное поведение.
